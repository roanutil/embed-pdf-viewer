# epdf-ops (Kotlin scaffold)

Thin Kotlin bindings over the PDFium engine in `crates/epdf-ops`, generated by uniffi from
`crates/epdf-uniffi/src/lib.rs` plus one hand-written file, `epdf-ops/src/main/kotlin/com/embedpdf/scaffold/Epdf.kt`,
that converts a rendered `Bitmap`'s BGRA bytes to the ARGB `IntArray` `android.graphics.Bitmap` and
Compose's `ImageBitmap` both want.

## Closing a document: `close()` vs `closeSync()`

`EpdfDocument` has two methods that both look like "I'm done with this document," and they do
different things.

uniffi's Kotlin generator makes every exported object implement `Disposable` and `AutoCloseable`,
and always emits its own `close()` for that: it frees the FFI handle and, on the Rust side, drops
`epdf_ops::Document`. `Drop` calls the non-blocking `drop_close()` (`crates/epdf-ops/src/engine.rs`),
which sets the closed flag immediately but only enqueues the underlying removal on the worker
thread. It does not wait for that removal to run.

`closeSync()` is epdf-uniffi's own `EpdfDocument.close`, renamed for Kotlin by `uniffi.toml`
because a class cannot declare two methods named `close()` and uniffi's generator claims that name
for `AutoCloseable`. It blocks until the removal has actually run. `crates/epdf-uniffi/src/lib.rs`
says why it exists at all: "Swift releases this object on ARC and would call it anyway; Kotlin
releases on the GC, whenever that is."

The gap between them shows up in ordinary, idiomatic Kotlin: `use { doc -> ... }` calls
`Closeable.close()`, the non-blocking path, not `closeSync()`. That is not a bug and nothing leaks;
the worker still processes the removal in order, it just does so on its own schedule. What `use`
alone gives up is the deterministic-cleanup guarantee `closeSync()` was built to provide: a
guarantee that, immediately after the call returns, the document's slot in the engine is actually
gone. Reach for that guarantee with an explicit `closeSync()` in a `finally`:

```kotlin
val doc = engine.open(bytes, password = null)
try {
    // ...
} finally {
    doc.closeSync()
}
```

The cost of doing this everywhere is that you give up `use`'s one-liner and the compiler's guarantee
that you called something. Reserve the explicit `finally` for call sites where the timing actually
matters, for example a test asserting the engine's document count right after close, or a caller
about to reopen the same file. Elsewhere, plain `use { }` is fine.

## Reading error text: `.message` vs `.detail`

uniffi's Kotlin generator gives every `OpsException` variant its own `override val message`, built
by formatting that variant's fields, not by copying the `thiserror` message text from
`crates/epdf-uniffi/src/lib.rs`. For most variants (`LoadFailed`, `PasswordRequired`, `RenderFailed`,
`Closed`) that field list is empty and `.message` is `""`. `PageOutOfRange` renders as
`"index=<value>"`.

`EngineFailed` and `Internal` each carry a field that was originally named `message` in the Rust
`OpsError`; `uniffi.toml` renames it to `detail` for Kotlin, because the generator's own
`override val message` collides with a Rust-side field of the same name. The result: `.message` on
those two variants renders as `"detail=<value>"`, not the thiserror sentence. An `EngineFailed`
whose `detail` is `"pdfium reinit failed"` has `.message` equal to the literal string
`"detail=pdfium reinit failed"`, not "the PDF engine failed and must be recreated: pdfium reinit
failed". Nothing is lost, the raw string is sitting right there in `.detail`, but a caller who logs
or surfaces `e.message` expecting the thiserror sentence gets a debug-looking field dump instead.

Treat `.message` as fit for a debug log, not for display. For `EngineFailed` and `Internal`, read
`.detail` for text meant to reach a person.

## Testing

`./gradlew :epdf-ops:test` runs `epdf-ops/src/test/kotlin/com/embedpdf/scaffold/VectorsTest.kt`
against real fixtures.

The six JVM tests now include exact DeviceRGB samples from the shared colored
fixture and a UTF-16 length assertion against the extracted text. Android device
coverage remains separate from these host JVM tests.
